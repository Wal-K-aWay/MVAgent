# 三模型统一旧9B src＋FFmpeg：结果分析

27B的14题补跑、Judge与最终审计已全部完成，三模型各330有效；最新27B分数见[补跑记录](recovery_27b.md)。下文原表保留补跑前的分析口径。

2026-10-16。结论：不支持把这套完整旧源码直接定为三模型唯一方案。9B的CV/MVU点估计提高但格式更差；35B的CV/MVU提高、Cross下降；27B的CV下降更明确。

本轮三模型都用**PRO6000的9B源码快照**，不是分别恢复三份不同的旧源码。105个src文件相同，唯一相对原9B快照的源码变化为media.py改FFmpeg。历史27B/35B使用不同的schema、字符限制和结构化生成路径，所以本实验不是其原设置的逐位复刻，也不是FFmpeg单因素消融。

## 格式与工程可靠性

| 模型 | 独立回答器格式不合格 | 上一轮直接 | 本次 | 有效回答中的空答案 / 仅右花括号 |
|---|---:|---:|---:|---:|
| 9B，300闭式题 | 71 | 7 | **15** | 0 / 0 |
| 27B，289有效闭式题 | 5 | 4 | **3** | 0 / 0 |
| 35B，300闭式题 | 14 | 8 | **4** | 0 / 0 |

各模型计数含CV431既有选项标签缺陷。格式不合格不等于JSON解析失败，例如9B在合法JSON里答Cannot determine仍不满足选择题要求。976份有效回答均非空、没有仅右花括号；27B另14份工程失败无可用答案，不能隐去后宣称每题都能答。

27B/CV存在10道上一轮直接答对、本次答错的题，例如CV421由B变A、CV703由D变C；这些都是合法选项。两臂CV格式不合格都只有1题，CV退步不能归因于新增格式错误或已剔除的服务故障。具体由哪条提示或取证策略引起，尚未做单因素消融。

27B失败链条：`crossvid:MOC:565`的一次短视频观察元数据为1.1秒/11帧/10fps，计划解码两帧，其中frame10读取失败，实际只剩1帧。Qwen预处理抛出`ValueError: t:1 must be larger than temporal_factor:2`，同步后端随后退出。原请求及此后同卡13题最终收到503/Connection refused；其中3道CCQA触发Judge前置断言。

这属于媒体预处理与服务恢复边界问题，不是reason超限、答案格式或H100显存不足的证据。缺帧尚未隔离到裁剪器或解码器的具体实现，不能直接认定FFmpeg本身错误。

## 建议与验证边界

不将完整旧9B src整体替换成三模型唯一正式基线。保留直接终答、耗尽兜底和FFmpeg的架构选择，分别评估格式与判断准确率。优先处理已经发生的有效帧检查和单副本失效，再在独立目录补测受影响14题、完成27B Judge，保留故障原件。

如果继续优化准确率，固定架构、媒体和数值设置，逐项对照Global提示/终答门槛、JSON schema生成路径、字段预算；当前整体回滚同时改变这些因素，不能识别单一因果。

本轮只离线分析，未修改正式src/Prompt/配置，未新增GPU推理或Judge。两模型105源文件、全部有效题完整输入、原始答案与日志截取的一致性均核验；27B详细调用核查完成。35B没有在本轮重新遍历完全部token日志，复用此前重复性冒烟，不能称最终全量审计已完成。

数据仍仅在Modal runs volume的`devbox/pro9_ffmpeg_20261016`、`pro9_ffmpeg_27b_20261016`、`pro9_ffmpeg_35b_20261016`。分析脚本`experiments/pro9_ffmpeg/quick_scores.py`；产物为`devbox/pro9_ffmpeg_large_20261016/analysis/quick_{27B,35B-A3B}.json`。CPU app为`ap-otcWsNbF7mTM82povGGJVk`。

## 样本量、效果波动与下一步（2026-10-16补跑后）

本批330道不同题：CV100、MVU100、Cross九闭式100＋CCQA30；三个模型测同一批，共990份有效结果。复用旧面板、改Prompt重测、补跑和重复性验收都不增加独立题目数。Cross的100题还分散到9类任务，单类约11题。

需要分别评价：同输入输出是否一致、任务能否正常交付、准确率是否提高。固定后端已通过范围的重复性验收可以复用；MOC565两遍都答B但标注为D，说明输出可重复与答对是两回事。修复14题工程失败也没有消除27B/CV相对直接协议的负差值。反过来，先前900对照的格式错误90→19说明已有明确工程收益。

每模型每benchmark约100题，当前很多配对差值区间仍约±10个百分点，确实难以稳定识别几百分点改进。若分布与相关性相似，样本扩大4倍，标准误大约减半；共享视频、分层权重和选择偏差仍须考虑。扩样用于提高判断精度，不会把真实负效应变成正效应。此前已有全量结果，但协议不同，不能充当最新正式实现的基线。

实际证据更支持分阶段诊断：CCQA1已在视觉观察阶段漏信息，35B报告仅47token且自然结束；27B NC1001/CV831在视觉输出反复罗列时间点并截断；Global终答并不是唯一薄弱环节。旧9B源码还同时改变了System、schema/字符预算、结构化生成路径和取证路线，整体回滚无法识别哪个组件有效。三个模型也不是严格只改变参数量的实验。

尚缺的主要受控实验（是计划，不是已验证结论）：

| 对照 | 固定什么 | 能回答什么 |
|---|---|---|
| 同帧观察指令、同观察文本的公开报告保真 | 模型、实际帧、预算、下游终答 | 是观察没有获取关键事实，还是VideoAgent报告压缩时丢失定义/时间/对象关系 |
| 同预算下联合观察与分视频取证、粗到细局部复查 | 总帧/调用预算及其他协议 | 当前路线是否丢失全局关系，局部复查是否真正增加关键证据 |
| 决策System与结构化生成方式的受控对照 | 相同逻辑schema、字段预算、媒体和数值配置 | 旧新差异来自决策指令还是生成约束；不再用整套src切换代替因果实验 |

前两类可利用现有watch_videos/analyze_videos/observe动作和公开报告字符串，保持架构与接口。详细策略进入skill；不向Global暴露VideoAgent内部轨迹，不使用隐藏答案作为在线证据。固定证据重放用于诊断，最终必须跑完整Agent验证总分。

粗到细取证可借鉴[VideoTree](https://arxiv.org/abs/2405.19209)，基于轨迹提出与验证文本策略可借鉴[GEPA](https://arxiv.org/abs/2507.19457)。这些只是可借鉴机制，不证明在本项目有效。GEPA此前已调研；scope也已有K1–K5探针，所测卡未显示超出安慰剂的效果，且常只改变首步而未执行后续追问。因此下一轮须同时记录策略是否真正执行、与安慰剂相比是否有净收益，不能把任何Prompt扰动都算作策略贡献。

建议顺序：

1. 冻结一套实际运行协议并补其准确率基线。当前正式History前置＋主动直接答＋耗尽独立兜底＋保留新版System的实现仍缺完整准确率对照；900直接面板和本批旧src都不等于它。使用既有330题，不再抽更小面板排名，不重跑不受影响的历史臂或一致性全矩阵。
2. 先用少量训练/开发轨迹定位观察、报告、决策、终答的首个失效环节，只推进1–2个证据最充分的候选。诊断样例不是准确率确认集。
3. Skill策略仅在既定CrossVid Train/Cal/Gate中迭代，optimizer只看Train公开轨迹；保留空库、安慰剂与真实策略对照。CV/MVU用于候选冻结后的迁移评估，不反复作为optimizer反馈。已反复查看的面板称开发集，不能声称未触碰Test。
4. 锁定候选后扩到新的确认面板，例如每benchmark约500题，并预先固定任务分层、视频来源隔离和统计方案。500不是保证识别2–3pp的门槛，具体需按配对翻转率规划；若要论文主结果，按原定CV997可测题、MVU1824、Cross Lite2500完整评估。
5. 区分MVAgent空库对E2E、进化库对同runtime空库两条对照。预先固定官方评分、E2E提示位置、CCQA Judge；逐模型×benchmark报告差值与区间、故障与格式诊断。不能用平均上涨代替九格均有提升，也不能把区间跨0当成准确率无损证明。

不追求把既有开发面板反复调到九格全正。若锁定方案在部分组合没有增益，应保留该结论；后续方法的目标是得到可解释、可复验的净收益。本节未启动新实验或更改正式配置。
