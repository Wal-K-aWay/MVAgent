## 调度与并行化分析（代码已核对，数值待本轮实测）

现有 `run_batch.py` 已通过空闲端点队列动态分配整题，每个 GPU 一次一题；本次则把同题的两次对照作为一个任务分配，确保配对硬件一致。单题内部 planner→观察→planner 存在数据依赖，不能把整条轨迹的所有模型调用同时发出。已经落地的独立工作并行是 RSI 四路抽帧；上一轮仅此媒体阶段快约 2.8–3.4 倍，整题热身后约快 4.1%。

可继续比较：

- 长任务优先：按视频时长排队，可能降低尾部空闲；时长并不等于推理时长，因此与动态 FIFO 同时报告。按已知真实耗时排序只能作为事后理想参考。
- 更多独立副本：模拟 4/8/16 卡的完成时间及分配 GPU 秒数，明确不包含冷启动、额外 CPU 争用和供给排队。增加卡数可能缩短时间但增加空闲成本；最后一条不可拆分的长轨迹仍决定尾部下限。
- 跨题 CPU/GPU 流水线：视频解码、图片编码与其他题的推理可以重叠。当前整题独占副本，媒体阶段会闲置该卡。若改为同卡多条问题协程、请求仍串行，需重新验证调用交错后的输入和完整 token；当前对照不改变这一规则。
- 单卡连续批处理/TP/EP：可能提高吞吐，但属于推理执行协议变化，应在独立候选上验证答案、稳定性、显存与真实吞吐。当前同步服务不能只增加客户端线程就获得连续批处理。[vLLM 并行策略说明](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/)
- 弹性资源：当前固定 8 卡 Sandbox 没有按队列自动增减卡数的实现。若改成独立单卡服务池，可以按待处理量启动/释放副本；Modal Function 池支持按输入压力扩缩容及动态修改容器数上下限，但需要改变部署编排，并计入模型加载时间。[Modal 扩缩容说明](https://modal.com/docs/guide/scale)

VAM 的独立机会是复用同一视频组的基础索引、把索引/embedding 与查询做流水线。适配器目前每题重新索引，且 embedding 服务固定批量 8；检索阶段已有异步调用。复用时要复制只含视频信息的基础库，隔离不同题产生的记忆。上一轮短题的索引占约 40–60 秒，但尚未做缓存对照，不能报告缓存的实测加速倍数；限制 FFmpeg 线程的候选曾在 5/6 媒体样本变慢，未采用。
