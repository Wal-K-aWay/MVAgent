# analyzer/prompts.py 中文镜像

仅供阅读，不被 Runtime 加载。

## TASK

# 批次问题分析

从所提供的开发案例中定位一种有依据、可复用的失败模式。先确定发生了什么问题；Skill 归因和修改规划属于 planner。

## 输入及其作用

- **cases**：各案例的原始输入、公开步骤、最终答案和离线反馈。案例可能成功或失败，同簇也可能需要不同方法。
- **input**：题目、选项及视频 ID/时长定义输入关系、任务标准和所需结果。
- **steps**：已记录的决策及返回结果。用原始输入与此前结果评估决策，用请求及其结果评估执行；结果只在动作结束后可用。
- **final_answer**：当前运行的最终答案；结合 input 和 steps 核对内容与格式。
- **offline_feedback**：参考答案与评分反馈说明结果差异，不揭示未观察的视频内容或错误原因。
- **omitted_case_ids**：未包含的案例，不能推断其轨迹。

本阶段不提供 Skill 文本、选卡记录或 VideoAgent 私有轨迹。

## 分析要求

1. 从各案例的输入确定主要任务和决定性证据需求，保留限定词、时间坐标、比较标准及答案内容。
2. 定位公开动作、参数、结果或后续使用结果的具体缺陷。区分请求不足、返回结果不足与后续决策误用；检查后续步骤是否已修复问题。
3. 用实际案例和步骤说明失败模式。区分记录事实与原因假设，不能把可能有效的补救方法当作原因的证明。
4. 比较相关成功行为和任务差异，保留有效行为；成功不证明因果关系，也不要求所有案例具有同一缺陷。
5. 只有非满分案例支持一个可供后续规划评估的具体缺陷时才输出 issue。只有答案错误、合理不确定性，或缺少公开决策补救依据的不可观察感知错误时，输出 no_issue。

例如，统计全视频总数却只请求开头片段，说明请求范围不足；压缩报告未提到事件不等于视频里没有事件；报告冲突需要评估如何协调，不能直接确定哪份报告错误。

## 阶段约束

- 各案例只使用自己的公开证据，不能跨案例移植观察。
- 引用真实轨迹步骤，而非策略编号。输入层要求可用 step=null；动作问题引用对应步骤。case_id 使用案例的 sample_id。
- 事件区间不证明观察覆盖范围，不编造私有观察。
- 不选择编辑操作、目标卡或卡库策略；Gate/Test 证据不可用。

## 输出格式

仅返回符合 Schema 的 JSON 对象，不加 Markdown 围栏或额外文字；所有字段都必须返回：
- **status**：issue 或 no_issue。
- **task_requirement**：可复用的任务与证据需求。
- **failure**：实际缺陷、受影响决策及其任务关联；原因的不确定性放在 hypotheses 或 uncertainties。
- **evidence_refs**：包含 case_id、step 的对象。issue 的依据包括非满分案例；no_issue 使用 []。
- **preserved_behavior**：应保留的成功行为，适当关联案例/步骤。
- **hypotheses**：可能解释，与已确定事实明确区分。
- **uncertainties**：缺失证据或限制结论的替代解释。

no_issue 的 failure 解释为何不支持可操作分析；其余不适用字段使用空字符串或空数组。
