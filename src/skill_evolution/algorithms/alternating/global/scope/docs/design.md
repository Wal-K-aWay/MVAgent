# Global Skill 自进化方案：以 Selector 的选择为聚类（global-scope-v1）

状态：设计稿第三版（2026-10-07），尚未实现。第一、二版分别按 task 和按预设的“题型签名”组织题目，已按用户意见放弃；本版不使用任何预设的题型分类。决定记录见第 12 节。

**一句话**：题目怎样分组，交给运行时的 Selector 决定。

- 卡库中每张卡的 when_to_use 是一段自由文本。Selector 读题后选中某张卡、或一张都不选，就把题目划分成若干组。
- 每张卡只在它被选中的题上起作用，因此只在这些题上测净收益。
- 每轮按测量结果修改 strategy 或 when_to_use，划分随之变化。这就是一种“动态聚类”：when_to_use 相当于聚类中心，Selector 的选择相当于分配。
- 新卡的适用题型由 optimizer 用自由文本描述，再由 Selector 落实成具体的题目集合。
- 只有在独立 Gate 上明确涨分的卡库才被接受。

## 1. 目标与约束

**目标**（用户提出）：

- 有合适 skill 时选到它并涨点；没有合适 skill 时保守地不选，保证不掉点；最终整体提升。
- 训练数据来自 CrossVid Lite2500 之外。
- 在 CVBench 和 MVU-Eval 上也希望有提升，所以 skill 必须是操作层面的、不绑定领域的方法。
- 流程可靠、通用、鲁棒；不依赖顶级 optimizer。当前 optimizer 是 GLM-5.3-Flash。

**约束**：

- MVAgent 架构冻结。只进化 Global 卡；Video 卡保持为空。
- **不使用任何预设的题型分类**（2026-10-07 用户要求）：
  - 系统看不到 CrossVid 的 task 类别；
  - 也不让模型从人为划定的类别中选择。
  
  题目的分组只来自 optimizer 的自由文本描述和运行时 Selector 的选择。task 只用于评估记账：分层抽样、官方总分、事后分析。
- **回答器不修**（2026-10-07 用户决定）。约 7% 的格式失败作为系统固有部分保留，处理方式见 5.4 节。
- **CVBench 和 MVU-Eval 只作纯 Test**（2026-10-07 用户决定），不参与任何选择。
- Actor 为 Qwen3.5-35B-A3B，temperature 0，thinking 关闭。**所有对比都在 H200 上、每副本并发 1 下运行**，这时推理是确定的。
- 沿用 CLAUDE.md 的硬性规则：
  - optimizer 只读 Train 的公开轨迹；
  - 候选只做整库评估，接受规则只看官方总分；
  - 原始 rollout 先落盘再评分；Judge 失败直接报错。

## 3. 核心思路：以 Selector 的选择作为聚类

### 3.1 为什么不用外部分组

| 分组方式 | 问题 |
|---|---|
| CrossVid task | 推理时看不到；task 内部题型不统一（E13）；按 task 校准路由，会让 when_to_use 记住模板措辞 |
| 题面 embedding 聚类 | 结果基本就是 task；对阈值和图参数敏感；题面相似不代表“同一张卡有用” |
| 预设的题型签名 | 取值范围是人为划定的，遇到范围外的题型或格式无法处理，泛化变差（用户意见） |

这三种方式有一个共同问题：分组规则与运行时选卡规则是两套东西，训练时的分组到了推理时并不存在。

### 3.2 用运行时机制本身分组

运行时只有一个分组机制：**Selector 读题，在卡库的 when_to_use 中选一张或不选**。本方案直接把它作为分组函数：

- 卡库 {c₁, …, cₖ} 把题目划分为 k+1 组：选中 c₁ 的题、……、选中 cₖ 的题、一张都不选的题（“空组”）。
- 每张卡的“范围”就是它被选中的那组题。按 E2，每张卡只影响这组题，所以只在这组题上测量它的效果，测到的就是部署时的真实效果。
- 新题型如果不符合任何 when_to_use 的描述，就落入空组，与空库行为完全相同。训练时如此，推理时也如此。

### 3.3 迭代（对应 k-means）

| k-means | 本方案 |
|---|---|
| 聚类中心 | 每张卡的 when_to_use 和 strategy |
| 把点分配给最近的中心 | 只跑 Selector，得到每张卡被选中的题 |
| 按分配结果更新中心 | 按每张卡在其选中题上的实测净收益：修改 strategy、修改 when_to_use（收窄或改写）、删卡 |
| 新增中心 | 从空组的失败题中，由 optimizer 用自由文本描述一类问题，写成新卡 |

几点区别：
- 分配不是按距离，而是由 Selector 按 when_to_use 的含义判断；
- 中心的好坏不看紧凑度，只看净收益；
- 中心之间互相竞争：新增或修改一张卡，可能把题从别的卡“抢走”。所以每次修改后都要对整库重新跑 Selector，再测量变化。

## 4. 设计原则

- **P1 只追求系统性收益，用测量把它和扰动分开。** 面板不按基线对错挑题；空库与候选逐题配对；先用安慰剂标定扰动；判定看净变化（变好题数减变差题数），并给出显著性。
- **P2 分组与范围都由运行时 Selector 决定。** 不使用 task、embedding 聚类或任何预设类别。卡的范围 = Selector 实际选中的题。
- **P3 优先保证不误选。** 由 E2，掉点只来自误选；一张卡在被选中的题上净收益不为正，就收窄它的 when_to_use 或删掉它。
- **P4 optimizer 的每个任务都小而单一，判断交给测量。** optimizer 负责提出假设：这类题出了什么问题、怎样改；是否有效由 Probe 和 Gate 测量决定。每类调用的输入都有明确上限。
- **P5 optimizer 只读 Train。** Probe 和 Gate 只向 optimizer 提供聚合数字，不提供题目、轨迹或 GT。
- **P6 不让 optimizer 依据单题成败下结论。** 由 E5，单题的变好或变差大多是扰动。给 optimizer 的样例总是成组出现，并标明“这组题的净变化”，要求它找的是多题共有的模式；无法找到时允许输出“未发现”。
- **P7 为迁移设计。** 卡用操作语言写，when_to_use 中不出现领域词；CVBench 和 MVU-Eval 只作纯 Test。

## 5. 数据划分

### 5.1 四个分区及其可见性

| 分区 | 来源 | 规模（第一阶段） | 用途 | optimizer 能看到什么 |
|---|---|---:|---|---|
| **T**（Train） | `src/skill_evolution/crossvid_clean_pool.json`，与 Lite2500 无共同视频来源 | 约 600 | 发现问题、写方法、修订；Selector 在 T 上的选择用来给 optimizer 提供样例 | 公开轨迹、Train GT、对错标签；**不含 task 代号和题号**，样例用 case_1、case_2 这样的局部编号 |
| **P**（Probe） | CrossVid 非 Lite 题，与 T 的视频来源隔离 | 1500（每 task 150），另有备用 1500 | 测量每张卡在其选中题上的净收益 | 只看到聚合数字 |
| **G**（Gate） | CrossVid 非 Lite 题，与 T 来源隔离，与 P 题号不重叠 | 1200（每 task 120） | 整库自然选卡评估，决定是否接受 | 只看到接受或拒绝 |
| **Test** | Lite2500、CVBench、MVU-Eval | — | 最终独立评估 | 不可见 |

- T、P、G 都按 task **等额**分层随机抽取。这样做是因为官方总分是十类 task 的等权平均，各 task 题数相同，P 和 G 上的统计才对应官方口径。这是评测方的安排，系统看不到。
- T 中 NC 只有 6 道、PI 只有 15 道干净题，就全部使用；其余 task 每类约 65 题。
- 备用 P：当某张卡在 P 上被选中的题太少、结论不显著时，用来扩大样本（8.2 节）。

**隔离规则**：

- T 与 P、G 之间按视频来源硬隔离：同一次录像、同一部电影、同一 UAV 序列都算同一来源，与 `prepare_crossvid_clean_pool.py` 的口径一致。
- P 与 G 之间至少题号不重叠，能做到时也按来源隔离。CC、FSA、NC 的视频在非 Lite 题中连成很大的连通分量，按来源隔离不可行；但 P 和 G 都不对 optimizer 可见，所以不构成内容泄漏，只是两者略有相关。
- MOC、MSR 的 T 要按航拍序列整体抽取。这两个 task 共 1160 题只来自 44 个序列（每个序列中位 30 题），同一序列的题看的是同一段画面，有的连答案都相同（例如 MOC:0/1/2 只换了目标车辆，答案都是 3 辆），所以一个序列的题只能放进同一个分区。从干净池随机抽 24+24 题会占掉 23 个序列，P+G 只剩 MOC 88、MSR 102 题；按序列整体抽取（4 个序列共 67 题）后，P+G 可用 MOC 378、MSR 397 题。切分脚本把每个 task 使用的序列数作为参数，以兼顾 Train 的场景多样性。

### 5.2 各 task 的容量

“可用于 P+G”指：从非 Lite 题中去掉 T，再去掉与 T 共用视频来源的题之后剩下的题数（按每 task 24 道 T 实测；T 增大到约 65 道时会略少，切分脚本会给出准确数字）。

| Task | 非 Lite | 干净池 | 可用于 P+G |
|---|---:|---:|---:|
| BU | 616 | 492 | 582 |
| CC | 580 | 36 | 404 |
| NC | 887 | 6 | 755 |
| PEA | 692 | 45 | 651 |
| FSA | 1632 | 202 | 1272 |
| PSS | 482 | 160 | 408 |
| MOC | 411 | 338 | 378* |
| MSR | 431 | 344 | 397* |
| PI | 151 | 15 | 136 |
| CCQA | 633 | 96 | 487 |

\* 按航拍序列整体抽取。

**PI 的容量不足**：P 和 G 合计每 task 需要 270 题，PI 只有 136 题，按比例分给 P 和 G（约 76 和 60），并在报告中说明 PI 的统计功效较低。

### 5.3 CVBench 和 MVU-Eval

只作纯 Test（用户决定），不参与任何选择。卡库冻结之后，在上面报告各卡的选卡率和净收益。

### 5.4 回答器格式失败（不修，按以下规则处理）

- 给 optimizer 选失败样例时，排除最终答案非法的题：退化输出、弃权、无法解析。
- 每次对比同时报告两边的答案合法率。合法率变化超过 2 个百分点时，单独标注，防止卡通过改变截断率“涨分”或“掉分”。
- 空库基线的分数照常包含这些题，与官方口径一致。

## 6. 算法流程

### 6.1 初始化（每次运行一次）

1. 冻结源码和配置快照，记录 commit、split、卡库哈希、模型与推理配置（沿用 `infra/store.py`）。
2. 生成并冻结 T/P/G 的 manifest。
3. **空库 rollout**：在 T、P、G 上各跑一次空库并缓存，以后所有对比都复用。备用 P 等到需要时再跑。
4. **复用检查**：从缓存中随机取 50 题重跑，确认结果与缓存逐字相同。不同就停止运行，说明确定性不成立。
5. **安慰剂标定**：在 P 中随机取 300 题，强制注入两段安慰剂文本，测出扰动翻转率和安慰剂净变化。
   - 如果安慰剂的净变化显著为负，说明基线对 prompt 过拟合，后续候选改为与安慰剂比较，而不是与空库比较。
   - 安慰剂文本：与候选卡长度相近，只重述现有规则，不引入任何新操作。

### 6.2 每一轮

```
当前库 L（初始为空）
每一轮:
  A 分配     只跑 Selector：L 在 T、P、G 上的选择 → 每张卡的选中题集合 + 空组
  B 新卡     从 T 空组的失败题中：
               B1 发现模式  Pattern finder → 至多 3 个“问题模式”（自由文本）+ 各自的 when_to_use 草稿
               B2 落实范围  对每个草稿：只跑 Selector（L + 草稿卡）→ 该草稿在 T 上选中的题；少于 8 道就放弃
               B3 写方法    Method writer（选中题中的失败与成功轨迹）→ strategy，可同时修订 when_to_use
  C 修订旧卡 对 L 中在 P 上净收益不显著或为负的卡：
               C1 Strategy refiner（选中题注入前后的变好/变差/仍失败案例）→ 新 strategy
               C2 Routing refiner（选中题中变差与变好的题面、该卡的 strategy）→ 收窄或改写的 when_to_use
  D 测量     每个候选库 L′（L + 一张新卡，或 L 中一张卡的一个修订版）：
               只跑 Selector → 选卡结果有变化的 P 题 → 只对这些题跑 rollout → 净收益 b−w 与显著性
               T 上同样只跑变化的题，产出下一轮给 optimizer 的样例
  E 选择     在本轮所有候选中，保留 P 上净收益显著为正、且没有任何一张卡在 P 上显著为负的候选库
             （有多个时取 P 上官方分最高者）；净收益显著为负、修订后仍无改善的卡标记为删除候选
  F Gate     每两轮，或候选库在 P 上通过时：在 G 上自然选卡，只重跑选卡有变化的题 → 判定接受或拒绝
  G 更新     接受则替换正式库；记录选卡统计、合法率、卡的长度
```

**为什么每个候选只改一处**：一次只加一张卡、或只改一张卡的一个字段，这样测到的变化可以归因到这一处修改。

### 6.3 各步骤细节

**A 分配**

用当前库对 T、P、G 全部题只跑 Selector。每次 Selector 调用只是一次短 LLM 调用（约 1000 token 输入、7 token 输出），3000 多题只需几分钟。卡库超过 8 张后，Selector 前的检索会启用 BM25 + embedding，与运行时一致。

**B1 发现模式（Pattern finder）**

- 输入：
  - T 空组中的失败题，至多 40 道，随机抽取，同一视频来源最多 1 道，排除非法答案的题。用 7.1 节的“摘要视图”，篇幅比完整轨迹小得多；
  - 同样来自 T 空组的成功题 10 道，用于对照；
  - 决策点清单（7.2 节）；
  - 当前库中各卡的 when_to_use，避免重复。
- 任务：找出至多 3 个“问题模式”。每个模式必须同时满足：
  - 覆盖至少 4 道失败题；
  - 能说清这类题有什么共同点，用题目本身的特征描述，而不是用题号或领域；
  - 能说清 GlobalAgent 的取证做法在这类题上哪里不对。

  找不到就输出“未发现”。
- 输出：每个模式包括
  - 一段描述（≤ 60 词）；
  - 涉及的 case 编号；
  - 选用的决策点；
  - 一份 when_to_use 草稿（≤ 80 词）。

模式用自由文本描述，不从任何预设列表中选。

**B2 落实范围**

- 把草稿 when_to_use 配上一个占位 strategy，加入当前库，只跑 Selector。Selector 只读 when_to_use，与 strategy 无关。
- 该草稿在 T 上被选中的题，就是这张新卡的初始范围。这一步把 optimizer 的文字描述，变成了运行时实际会选中的题目集合。
- 被选中的 T 题少于 8 道时放弃这个模式：要么描述太窄，要么 Selector 不认可。
- 如果草稿“抢走”了已有卡的大量题（超过该卡选中题的 30%），也放弃，留待后续轮次处理。

**B3 写方法（Method writer）**

- 输入：
  - 模式描述和 when_to_use 草稿；
  - B2 中被选中的 T 题：失败 6 道、成功 4 道，用 7.1 节的完整视图；
  - 决策点清单。
- 输出：
  - strategy（长度规则见 7.3 节）；
  - 修订后的 when_to_use（可以不改）。如果修订了，就重做 B2。
  - 一句“预期变化”。

**C1 修订方法（Strategy refiner）**

- 输入：当前 strategy，以及该卡在 T 上选中题的注入前后对比：变好 4 道、变差 4 道、仍失败 2 道，并给出这组题的净变化 b−w。
- 输出：修订后的 strategy 和一句修改说明，或者“未发现可改进之处”。只针对多道题共有的差异修改（P6）。
- 每次修订，篇幅最多比上一版增加 30%。

**C2 修订路由（Routing refiner）**

- 输入：当前 when_to_use 和 strategy；该卡在 T 上选中题中的变差题面 8 道、变好题面 8 道，只给题面，并给出净变化。
- 任务：判断变差的题是否有一个可以用题面描述的共同特征，可以据此把它们排除在外；有就收窄或改写 when_to_use，没有就输出“未发现”。
- 输出：when_to_use（≤ 80 词）。
- 同时给出 strategy，是为了让 when_to_use 与方法保持一致，避免 cv2r 那样描述与方法错位。

**D 测量**

- 对每个候选库只跑 Selector，找出选卡结果与当前库不同的题，只对这些题跑 rollout，其余直接复用缓存（E1、E2）。
- 统计对象是“选卡结果有变化的 P 题”。判定规则见 8.2 节。

**E 选择**

- 每轮可能有多个候选（新卡、修订后的 strategy、修订后的 when_to_use）。只保留 P 上净收益显著为正、且没有任何一张卡在 P 上显著为负的候选。
- 卡在 P 上显著为负、并且修订两次仍没有改善时，生成一个“删掉这张卡”的候选库，同样经过 D 测量和 Gate。

**F Gate**

- 只跑 Selector，找出 G 上选卡结果有变化的题，只重跑这些题。
- 判定规则见 8.3 节。

## 7. 大模型调用的输入输出规范

### 7.1 两种轨迹视图

**摘要视图**（只用于 Pattern finder，一次需要看很多题）：

| 字段 | 内容 | 上限 |
|---|---|---|
| 编号 | case_1、case_2 这样的局部编号；不出现题号、task 代号或 benchmark 名称 | — |
| 题面 | 题干与选项，去掉 benchmark 的指令外壳 | 400 字符 |
| 动作骨架 | 每一步的 action，以及 instruction 的前 150 字符；`watch_videos` 加上片段 | — |
| 报告要点 | 每个视频报告 Summary 的第一句 | 每条 150 字符 |
| 结果 | 最终答案、正确答案、对错 | — |

**完整视图**（用于 Method writer 和 Strategy refiner）：

| 字段 | 内容 | 上限 |
|---|---|---|
| 编号、题面、视频 | 同上；题面不截断；视频给出 ID 与时长 | — |
| 每一步 | action；`analyze_videos` 的逐视频 instruction 原文；`watch_videos` 的 instruction 和片段；VideoAgent 报告的 Summary | 每条 Summary ≤ 600 字符，超出部分截断并标注“[truncated]” |
| 结果 | 最终答案、对错标签（pass/partial/fail）、正确答案 | — |
| 对比（仅 Strategy refiner） | 同一题注入前后的轨迹并列展示 | — |

**两种视图都不放入的内容**：
- Global 的 reason，篇幅大且多为重复；
- 原始路由事件、卡的全文副本、哈希、缩进空白。在 cv2r 中这些占输入的 50% 以上。

**总长度上限**：每次调用约 40K 字符。超出时按“题”整道丢弃，并在输出中标注丢弃了哪些题。上限要为后续追加的内容预留空间，避免 cv2r 那样作者输入超限、整个候选被丢弃。

### 7.2 决策点清单（提示，不是限制）

清单列出 GlobalAgent 层面可以改变的决策点，以及每个决策点的已知证据。它描述的是固定的 action 空间，而不是题目的分类；optimizer 可以选清单之外的决策点，但要说明理由。

1. **逐视频 instruction 的写法**：中性、可比较的描述，而不是“有没有 X？”（E4）；要求报告哪些可见细节；保留题目中的限定条件。
2. **动作选择**：何时用 `analyze_videos`、何时用 `watch_videos`；联合观看时传哪些视频、怎样写 instruction（E6、E7）。必须遵守 action 规则，不能让视觉模型直接选答案；可以要求它逐个选项报告可见的支持或反对证据。
3. **片段与覆盖**：长视频是否先定位再细看；联合观看时视频越多，每个视频分到的帧越少。
4. **追问的触发条件**：报告分不出候选、或互相矛盾时，对哪几个候选、用什么样的问题追问（E4）。
5. **何时回答**：证据足够区分候选时停止。

清单不包含答案格式规则，因为回答器不接收 skill（E11）。

### 7.3 输出 Schema 与长度规则

| 调用 | 输出字段 | 程序检查 |
|---|---|---|
| Pattern finder | 至多 3 个模式：`description`（≤ 60 词）、`cases`（≥ 4 个 case 编号）、`decision_point`、`draft_when_to_use`（≤ 80 词）；或“未发现” | case 编号合法；领域词检查 |
| Method writer | `strategy`、`when_to_use`（≤ 80 词）、`expected_change`（≤ 60 词） | 长度；领域词和泄漏检查 |
| Strategy refiner | `strategy`、`change_summary`（≤ 60 词），或“未发现” | 与原文不能相同；长度和增幅；领域词和泄漏检查 |
| Routing refiner | `when_to_use`（≤ 80 词）、`excluded_feature`（≤ 40 词），或“未发现” | 与原文不能相同；领域词检查；不能出现 task 代号或 benchmark 名称 |

**strategy 的长度**（待确认，第 12 节）：
- **硬上限 600 词**（运行时原有上限 1200 词）；
- prompt 中建议 150–350 词，并且只针对一个决策点；
- 每次修订，篇幅最多比上一版增加 30%；
- 每张卡都记录长度和测得的效果，阶段 1 结束后据此复核上限。
- 理由：没有数据能说明某个具体数值最好；但 cv2r 的卡在修订中从 420 词膨胀到 851 词而没有收益，项目旧结论也记录了“Generator 容易写出超长、领域过窄的卡”，所以不建议完全不设限。

所有调用都按现有方式保存输入、原始输出、校验结果和 usage，可以恢复。按项目规则，英文 prompt 同时维护中文镜像（`chinese_prompts/`）。

### 7.4 程序检查

- **领域词**：when_to_use 中不能出现 CrossVid 的领域词，例如烹饪、食谱、电影、角色、无人机、UAV、装配、玩具车。strategy 中出现时只给警告，因为方法内容可能确实需要举例。词表在实现时从 T 题面的高频名词中整理，并人工核对。
- **泄漏审计**：strategy 和 when_to_use 中不能出现视频文件名、视频 ID 以外的媒体标识、T 题的具体时间点；与 T 中报告原文的 8-gram 重合不能超过 3 处。
- **抢题检查**：新卡或修订后的 when_to_use 如果让某张已有卡丢掉超过 30% 的选中题，要单独标注；它的测量要同时报告被抢走的那部分题的变化。

## 8. 统计与判定规则

### 8.1 “变化”的定义

沿用 `scoring.py` 的 `CHANGE_MARGINS`：
- 选择题：对错翻转才算变化；
- FSA：IoU 变化 ≥ 0.2；
- CCQA：变化 ≥ 1/3。

变好题数记为 b，变差题数记为 w。

### 8.2 P 上的判定（每个候选库）

- 统计对象：选卡结果与当前库不同的 P 题。
- **通过**：单侧符号检验 p ≤ 0.05（只看变化了的题，b 对 w）。
- **否决**：w ≥ b + 3。
- **扩大样本**：既没通过也没被否决、并且选卡有变化的 P 题少于 200 道时，在备用 P 上以 500 题为一块追加：先只跑 Selector，再只对有变化的题跑 rollout，直到通过、被否决，或用完备用 P。
- 参考检出能力（取翻转率 d=0.17–0.33；n 为选卡有变化的题数）：
  - n=200 约可检出 +6–9 分；
  - n=300 约可检出 +4–6 分。
  - 效果更小的卡在这个预算下测不出来，会被记为不显著。

### 8.3 Gate 的接受规则（用户已确认）

对候选库与当前库在 G 上逐题配对，同时满足三条才接受：

1. G 上的官方总分提高：CrossVid task 等权 macro，子集上按全集 task 题数分层估计，与 `HierarchicalScoreAggregator` 口径一致；
2. 选卡有变化的题上，单侧符号检验 p ≤ 0.10；
3. 没有任何一个 task 出现 w ≥ b + 3。

第 2、3 条是对“只看官方总分”的统计化解释：仍然只看官方总分，但要求提高的幅度超出扰动噪声。

### 8.4 多重比较

P 被多个候选反复使用，P 上的最好结果会偏乐观。由于 G 的题与 P 不重叠，Gate 起到独立确认的作用；最终的结论只依据 G 和 Test，不依据 P。

### 8.5 报告

每次对比都报告：
- 每张卡的选卡率（总体，以及事后按 task 拆分）、选中题上的 b 和 w；
- 各 task 的官方分差、答案合法率；
- 安慰剂的翻转率；
- 卡的长度。

## 10. 实施计划

**阶段 0：基础设施**（时间预算 2 天；主要在本机写代码，GPU 只用于最后的冒烟测试）

1. 切分脚本：生成 T/P/G/备用 P 的 manifest，包含来源隔离、MOC/MSR 按序列抽取、按 task 等额分层，并输出可行性报告。
2. Selector-only 执行器：对一个卡库和一批题只跑 Selector（直接调用 `select_skills`），输出每题的选择；比较两个卡库的选择差异。
3. 增量 rollout：对“选卡有变化的题”跑 rollout，其余复用缓存；复用 `FrozenMVAgentExecutor` 和 rollout 缓存。
4. 安慰剂的强制注入：把文本写成静态 skill（`load_skill` 路径）；核对静态注入与动态注入渲染出的 prompt 逐字相同。
5. 配对统计模块：计算 b、w、显著性、扩大样本的规则、官方分差、合法率，复用 `aggregation.py`。
6. 两种轨迹视图：复用 `infra/trajectory.py` 的公开轨迹投影，增加长度上限、局部编号与丢弃记录。
7. 四类 optimizer 调用的 prompt、schema 和中文镜像。
8. 状态持久化与恢复，复用 `infra/store.py`。
9. Modal 冒烟测试：20 题跑通完整的一轮，并贴出实际输出。

**阶段 1：第一个端到端实验单元**（时间预算 1 天，GPU 约 8–9 h）

依次完成：切分 → 空库 rollout → 复用检查 → 安慰剂标定 → 从空库开始跑 2–3 轮 → Gate。

产出：
- 主指标：G 上的官方总分变化，以及各 task 的 b 和 w；
- 每张卡的选卡率、选中题上的净收益、合法率、卡的长度；
- 被放弃的模式和候选，以及放弃原因；
- 更新 `.claude/status.md`。

无论结果正负，都如实记录。

**阶段 2：继续迭代**

按 6.2 节的轮次继续，直到连续 3 轮没有候选通过 Gate，或用完预算。每轮的发现、修订和删除都在同一个循环里进行。

**阶段 3：独立评估**

- 冻结最终库，在 Lite2500、CVBench、MVU-Eval 上分别与空库对比。
- 报告每张卡在每个 benchmark 上的选卡率、选中题上的 b/w，以及官方总分。
- 在 Lite2500 上按“视频来源是否与训练用视频重叠”分组比较涨幅。T 全部来自干净池，理论上没有重叠。

**停止条件**：每个阶段超出时间预算时，先缩小非必要范围（减少每轮的候选数、减少备用 P 的使用），不放弃端到端测量。

## 11. 风险，以及目前不能声称的结论

- **效果可能小于检出能力。** 历史上手写的 skill 都没有显著效果（E9）。可能的结果是没有任何卡通过 Gate；这本身就是有价值的负结果，会如实记录各候选的 b、w 和置信区间。
- **Pattern finder 可能把噪声当成模式。** 由 E5，单题的成败大多是扰动，optimizer 可能“找到”并不存在的共同点。B2 和 D 会在 T 之外的 P 上测量，假模式通不过；代价是浪费预算。如果连续几轮都是如此，就降低每轮的模式数。
- **Selector 是否认可 optimizer 的描述。** optimizer 写的 when_to_use 如果过于抽象，Selector 可能几乎不选或乱选。B2 会立即暴露这一点：选中的 T 题太少，或者选中的题明显不对。
- **卡之间互相抢题。** 新卡可能把题从已有卡抢走，使已有卡的效果变化。测量只看选卡有变化的题，所以抢走的部分也会被计入；抢题超过 30% 时单独标注。
- **范围不对应任何可命名的类别。** 卡的范围就是 Selector 选中的题，事后可以按 task 拆开分析，但不保证与 task 对齐。这是本方案有意的取舍。
- **Selector 在 CVBench 和 MVU-Eval 上的行为未知。** 两者是纯 Test，只能在阶段 3 看到结果。
- **回答器的格式失败不修**（5.4 节）。卡如果改变了 `reason` 的长度，可能通过截断率影响分数。这一项会被监测，但无法从分数中完全剔除。
- **确定性依赖于固定的硬件和并发设置。** 换卡、换 vLLM 版本或改并发都会破坏缓存复用，必须重新做复用检查。

**目前不能声称**：任何 Global skill 能带来净提升；CrossVid 上训练出的卡能迁移；联合观看在全体题目上有净收益。

## 12. 决定记录

**已确认（2026-10-07）**：
- CVBench 和 MVU-Eval 只作纯 Test。
- Gate 接受规则采用 8.3 节的统计化解释。
- 第一阶段预算：GPU 约 8–10 h，约 300–400 美元。
- 回答器不修。
- 不使用任何预设的题型分类：系统看不到 task 类别，也不使用预设的签名类别。

**待确认**：
1. 本版的核心做法：以 Selector 的选择作为分组和范围，新卡的题型由 optimizer 用自由文本描述（第 3 节）。
2. strategy 长度规则：硬上限 600 词、建议 150–350 词、每次修订增幅 ≤ 30%（7.3 节）。

| 新卡从哪里来 | analyzer 诊断某个簇 | 按组提出 | 空组失败题中由 optimizer 用自由文本描述的模式 |
| optimizer 可见数据 | Train，以及 Cal 题连同 GT | 只有 Train | 只有 Train，且不含 task 代号和题号 |
| 接受规则 | Gate 总分严格提高 | Gate 总分提高且超出扰动噪声 | 同第二版 |
| strategy 长度 | 上限 1200 词（实际膨胀到 851 词） | 400 / 600 词 | 硬上限 600 词，建议 150–350 词 |

**可复用的部分**：`infra/` 中的 rollout、缓存、评分、聚合、公开轨迹投影和持久化；`mvagent/skills` 的运行时、Selector 和检索；cluster_v2 中的 CARD_CONTRACT 和 action 背景说明（作为 prompt 素材）。
