# Global Skill 自进化方案：实测范围（global-scope-v1）

状态：设计稿第二版（2026-10-07），尚未实现。已确认和待确认的决定见第 12 节。

**一句话**：先测量，再写路由。

- optimizer 根据 Train 轨迹提出一张卡的方法（strategy）。
- 这张卡用在哪些题上，由“强制注入后逐题配对的净收益”决定。
- 题目用 Actor 模型只读题面就能得出的**题型签名**来分组，系统在任何环节都看不到 CrossVid 的 task 类别。
- when_to_use 按实测范围来写，并用只跑 Selector 的离线检查校准。
- 只有在独立 Gate 上明确涨分的卡库才被接受。

---

## 1. 目标与约束

**目标**（用户提出）：

- 有合适 skill 时选到它并涨点；没有合适 skill 时保守地不选，保证不掉点；最终整体提升。
- 训练数据来自 CrossVid Lite2500 之外。
- 在 CVBench 和 MVU-Eval 上也希望有提升，所以 skill 必须是操作层面的、不绑定领域的方法。
- 流程可靠、通用、鲁棒；不依赖顶级 optimizer。当前 optimizer 是 GLM-5.3-Flash。

**约束**：

- MVAgent 架构冻结。只进化 Global 卡；Video 卡保持为空。
- **回答器不修**（2026-10-07 用户决定）。约 7% 的格式失败作为系统固有部分保留，处理方式见 5.4 节。
- **系统看不到 task 类别**（2026-10-07 用户要求）。推理时只能靠理解题目来判断，所以训练时 optimizer 的输入、卡的范围和路由标签都不使用 task 标签。task 只用于评估记账：分层抽样、官方总分、事后分析。
- **CVBench 和 MVU-Eval 只作纯 Test**（2026-10-07 用户决定），不参与任何选择。
- Actor 为 Qwen3.5-35B-A3B，temperature 0，thinking 关闭。**所有对比都在 H200 上、每副本并发 1 下运行**，这时推理是确定的。
- 沿用 CLAUDE.md 的硬性规则：
  - optimizer 只读 Train 的公开轨迹；
  - 候选只做整库评估，接受规则只看官方总分；
  - 原始 rollout 先落盘再评分；Judge 失败直接报错。

## 3. 设计原则

- **P1 只追求系统性收益，用测量把它和扰动分开。**
  - 面板不按基线对错挑题；空库与候选逐题配对比较；
  - 先用安慰剂（同样长度、不含操作内容的文本）标定扰动有多大；
  - 判定看净变化（变好题数减变差题数），并给出显著性。
- **P2 适用范围由实测收益决定，不由作者声明。** 作者只写方法；“这张卡管哪些题”由强制注入的净收益决定；when_to_use 按这个范围编写，并离线核对选卡结果。
- **P3 优先保证选卡精确。** 由 E2，掉点只来自误选；对没有合适卡的题，宁可漏选，也不误选。
- **P4 optimizer 的每个任务都小而单一，判断交给测量。** 三类调用（写方法、修方法、写路由）各自的输入都有明确上限，并提供一份“可改变的决策点”清单，不要求 optimizer 自己想出整套方法。
- **P5 optimizer 只读 Train。** Probe 和 Gate 只向 optimizer 提供聚合数字，不提供题目、轨迹或 GT。
- **P6 为迁移设计。**
  - 卡用操作语言写；
  - CVBench 和 MVU-Eval 只作纯 Test；
  - 迁移靠两件事间接保证：一是题型签名本身就是跨 benchmark 通用的操作描述；二是同一签名组的收益要在不同来源领域（如室内日常、烹饪、电影）的题上都成立。
- **P7 系统只依据题目本身组织和路由。** 分组、范围和路由标签都用题型签名，签名由 Actor 模型只读题面得出；task 标签只用于评估记账。

## 4. 为什么不再按题面聚类，也不按 task 组织

| 思路 | 判断 | 理由 |
|---|---|---|
| 改进 embedding 聚类，让聚类更精准 | 不采用 | CrossVid 题面由模板生成，聚类结果基本就是 task，对阈值和图参数敏感。而且真正难的不是把训练题分组，而是判断一张卡在哪些题上**有用**，题面相似度回答不了这个问题（E5） |
| 直接按 CrossVid task 组织 | 不采用 | 推理时看不到 task；task 内部的题型并不统一（E13）；按 task 校准路由，会让 when_to_use 记住模板措辞 |
| **题型签名**：由 Actor 模型只读题面，填写固定格式的离散字段 | **采用** | 签名是推理时同样能拿到的信息，由与 Selector 相同的模型得出，所以“按签名选卡”是 Selector 原则上能做到的事；每个字段都是离散类别，没有阈值或图参数；字段描述的是多视频问答的通用操作，三个 benchmark 都适用 |
| 动态聚类（像 k-means 一样把 skill 信息纳入迭代） | **采用其思想，换掉距离** | “题属于哪张卡”由注入后的净收益决定，而不是由距离决定。E 步：在各签名组上测量每张卡的净收益，确定范围；M 步：用范围内的成功和失败轨迹修订方法，并按范围重写 when_to_use |
| 重跑现有流程看看哪里能突破 | 不优先 | cv2r 已经暴露了结构性问题（E10）；在 E3 的扰动水平下，Gate 每类 4 题、总共 36 题的设计，原理上就测不出 +2–5 分的效果 |

## 5. 数据划分

### 5.1 四个分区及其可见性

| 分区 | 来源 | 用途 | optimizer 能看到什么 |
|---|---|---|---|
| **T**（Train） | `eval/crossvid_clean_pool.json`，与 Lite2500 无共同视频来源 | 运行空库和带卡的 rollout，为写方法、修方法、写路由提供样例 | 公开轨迹、Train GT、对错标签；**不含 task 代号和题号**，样例用 case_1、case_2 这样的局部编号 |
| **P**（Probe） | CrossVid 非 Lite 题，与 T 的视频来源隔离；**按签名组抽取** | 强制注入测量、确定范围、离线核对选卡 | 只看到聚合数字（每个签名组的变好/变差题数、选卡精确率和召回率） |
| **G**（Gate） | CrossVid 非 Lite 题，与 T 来源隔离，与 P 题号不重叠；**按 task 分层抽取** | 整库自然选卡评估，决定是否接受 | 只看到接受或拒绝 |
| **Test** | Lite2500、CVBench、MVU-Eval | 最终独立评估 | 不可见 |

- P 按签名组抽取，是因为 Probe 要检验的是“这张卡对这类题有没有用”。
- G 按 task 分层抽取，是因为官方总分是 CrossVid 十类 task 的等权平均，G 要估计的是这个总分。
- 这种分层是评测方的安排，系统看不到。

**隔离规则**：

- T 与 P、G 之间按视频来源硬隔离：同一次录像、同一部电影、同一 UAV 序列都算同一来源，与 `prepare_crossvid_clean_pool.py` 的口径一致。
- P 与 G 之间至少题号不重叠，能做到时也按来源隔离。CC、FSA、NC 的视频在非 Lite 题中连成很大的连通分量，按来源隔离不可行；但 P 和 G 都不对 optimizer 可见，所以不构成内容泄漏，只是两者略有相关。
- MOC、MSR 的 T 要按航拍序列整体抽取。这两个 task 共 1160 题只来自 44 个序列（每个序列中位 30 题），同一序列的题看的是同一段画面，有的连答案都相同（例如 MOC:0/1/2 只换了目标车辆，答案都是 3 辆），所以一个序列的题只能放进同一个分区。从干净池随机抽 24+24 题会占掉 23 个序列，P+G 只剩 MOC 88、MSR 102 题；按序列整体抽取（4 个序列共 67 题）后，P+G 可用 MOC 378、MSR 397 题。切分脚本把每个 task 使用的序列数作为参数，以兼顾 Train 的场景多样性。

### 5.2 各 task 的容量

“可用于 P+G”指：从非 Lite 题中去掉 T，再去掉与 T 共用视频来源的题之后剩下的题数（实测）。

| Task | 非 Lite | T（干净池） | 可用于 P+G |
|---|---:|---:|---:|
| BU | 616 | 24 | 582 |
| CC | 580 | 24 | 404 |
| NC | 887 | 6 | 755 |
| PEA | 692 | 24 | 651 |
| FSA | 1632 | 24 | 1272 |
| PSS | 482 | 24 | 408 |
| MOC | 411 | 24* | 378* |
| MSR | 431 | 24* | 397* |
| PI | 151 | 15 | 136 |
| CCQA | 633 | 24 | 487 |

\* 按航拍序列整体抽取；随机抽取时只剩 88 和 102。

T 每个 task 取 24 题（NC 只有 6 题、PI 只有 15 题），是为了保证每个 task 的题都出现在 Train 里。抽取时不看签名，也不把 task 告诉 optimizer。

**第一阶段的 P 和 G 规模**：
- P：目标签名组约 600 题，按 50 题一块序贯使用；相邻签名组和其余签名组各 20–40 题，用于伤害检查和路由反例。
- G：目标签名组集中的 task 各 200 题，其余 task 各 40 题，共约 900 题。
- 具体抽法在签名标注完成后、读任何结果之前确定，并冻结在切分 manifest 里。

### 5.3 CVBench 和 MVU-Eval

只作纯 Test（用户决定），不参与任何选择。卡库冻结之后，才给它们的题标注签名，用于报告各签名组的覆盖率和选卡率。

### 5.4 回答器格式失败（不修，按以下规则处理）

- 给 optimizer 选失败样例时，排除最终答案非法的题：退化输出、弃权、无法解析。
- 每次对比同时报告两边的答案合法率。合法率变化超过 2 个百分点时，单独标注，防止卡通过改变截断率“涨分”或“掉分”。
- 空库基线的分数照常包含这些题，与官方口径一致。

### 5.5 题型签名

**作用**：取代 task，作为“写方法时的取样分组、Probe 的分层、范围、路由正例和反例”的单位。

**标注者**：Actor 模型（Qwen3.5-35B-A3B，temperature 0，thinking 关闭），与 Selector 是同一个模型。

**输入**：题目文本和选项（去掉 benchmark 的指令外壳）、视频个数和时长。不给 GT、task、题号或视频内容。

**输出**（固定 JSON，字段取值是封闭的枚举，外加 `other`）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `answer_form` | `one_video`、`video_subset`、`option_content`、`number`、`order`、`time_interval`、`free_text`、`yes_no` | 题目要求的答案是什么 |
| `operation` | `check_condition_per_video`、`compare_across_videos`、`order_events`、`locate_interval`、`count`、`spatial_relation`、`infer_unseen`、`summarize_theme`、`external_knowledge`、`find_relevant_video` | 要得出答案，必须完成的主要操作 |
| `evidence_scope` | `separate`、`joint` | 证据能否逐视频分别获得，还是需要把多个视频放在一起比较 |

- 这套字段描述多视频问答的通用操作，与 GlobalAgent 的动作空间对应，不针对任何一个 benchmark。
- **签名组**：以 `operation` 为主分组，`answer_form` 用于在组内进一步细分（例如区分“选出视频”和“选出选项内容”）。
- **标注成本**：每题一次短文本调用，CrossVid 全部 9015 题约 10 分钟。

**质量检查**（阶段 0，只作检查，不作优化目标）：
1. 与 task 做交叉表：同一模板的题应集中在少数签名上。如果某个 task 的签名非常分散，要人工抽查是题型确实不同，还是标注不稳定。
2. 抽查 100 题，人工判断签名是否合理，报告一致率。
3. 稳定性：换一种等价的 prompt 措辞重标 300 题，报告字段一致率。

**与运行时的关系**：签名只在离线使用，运行时不变，Selector 仍然只看题目和 when_to_use。路由校准（6.3 节第 5 步）检查的是：Selector 能否只靠 when_to_use 选中签名属于范围内的题。

## 6. 算法流程

### 6.1 初始化（每次运行一次）

1. 冻结源码和配置快照，记录 commit、split、卡库哈希、模型与推理配置（沿用 `infra/store.py`）。
2. **签名标注**：给 CrossVid 非 Lite 题（T、P、G 的候选池）标注签名，并做 5.5 节的质量检查。然后按签名组抽取 P、按 task 抽取 G，冻结 manifest。
3. **空库 rollout**：在 T、P、G 上各跑一次空库并缓存，以后所有对比都复用。
4. **复用检查**：从缓存中随机取 50 题重跑，确认结果与缓存逐字相同。不同就停止运行，说明确定性不成立。
5. **安慰剂标定**：在第一阶段目标签名组的 P 上取 300 题，强制注入两段安慰剂文本，测出扰动翻转率和安慰剂净变化。
   - 如果安慰剂的净变化显著为负，说明基线对 prompt 过拟合，后续候选改为与安慰剂比较，而不是与空库比较。
   - 安慰剂文本：与候选卡长度相近，只重述现有规则，不引入任何新操作。

### 6.2 每个“目标签名组”的工作循环

```
for 目标签名组 S（第一阶段：check_condition_per_video）:
    1 提出方法  Proposer(T 中签名属于 S 的失败与成功轨迹, 决策点清单) → 2 个候选 strategy（各针对不同的决策点）
    2 强制注入测量  对每个候选：在 P_S 上序贯注入，与空库逐题配对 → 净收益
                    同时在 T_S 上注入，产出供修订用的轨迹
    3 确定范围      范围 = 显著为正的签名组（先测 S，再测与 S 共享 operation 或 answer_form 的相邻组）；
                    排除集 = 显著为负的组；S 本身都不显著 → 放弃该候选
                    在其余签名组的 P 上各注入 20 题，检查明显伤害
    4 修订方法（至多 2 次）  Refiner(范围内 T 题注入前后的变好/变差案例) → 新 strategy → 回到 2（只测范围内的组）
    5 写路由并校准  Router(目标操作说明, T 中范围内的题面, T 中范围外的题面, 已有卡的 when_to_use) → when_to_use
                    只跑 Selector：在 T 上迭代修改（每次反馈误选/漏选的 T 题面），最终在 P 上核对精确率和召回率
    6 整库 Gate     候选库 = 当前库 + 新卡；在 G 上自然选卡；只重跑选卡结果有变化的题 → 判定接受或拒绝
    7 更新状态      接受则替换正式库；记录范围、选卡统计和合法率
```

**与 k-means 的对应**：第 2–3 步相当于 E 步，测出“哪些题归这张卡”；第 4–5 步相当于 M 步，按这些题更新卡的方法和路由描述。两个步骤迭代，直到范围不再变化或达到预算上限。

### 6.3 各步骤细节

**第 1 步：提出方法（Proposer）**
- 输入取自 T 中签名属于目标组的题：
  - 6–8 道失败题，已排除非法答案的题；在组内随机抽取，同一视频来源最多取 1 道，以保证多样性；
  - 3–4 道成功题；
  - 一份决策点清单（见 7.2 节）。
- 输入里不出现 task 代号、题号或 benchmark 名称。
- 每次生成 2 个候选，必须选择不同的决策点。例如一个改“逐视频 instruction 的写法”，另一个改“何时改为联合观看”。
- strategy 长度规则见 7.3 节：硬上限 600 词，建议 150–350 词。
- 同时输出一句“目标操作说明”，这是写路由的输入，不是 when_to_use。

**第 2 步：强制注入测量（Probe）**
- 注入方式：把卡渲染后的正文写成静态 skill（`load_skill` 路径），保证 Actor 看到的文本与自然选卡时完全一致。实现时要逐字比较两条路径渲染出的 prompt。
- 按签名组序贯测量：每块 50 题，最多测到该组 P 的规模。判定规则见 8.2 节。
- 每块内按 task 分层，以免某一块恰好集中在某个来源领域。分层只是抽样安排，不进入任何判定。
- 在 T 上同样注入，产出供第 4 步修订用的“注入前后”轨迹对。这部分 optimizer 可读，不计入范围判定。

**第 3 步：确定范围**
- 范围：在 P 上显著为正的签名组集合。
- 排除集：显著为负的签名组。
- **伤害检查**：在其余签名组的 P 上各注入 20 题。如果某组的净变化 ≤ −3 题，就把它加入排除集，并在第 5 步作为重点反例。
- **跨领域检查**（只用于报告）：事后按来源领域（如室内日常、烹饪、电影）拆开组内的 b 和 w。如果收益只集中在一个领域，就在报告中标为“未证明可迁移”。这一步用到 task 标签，但只用于分析，不影响任何选择。

**第 4 步：修订方法（Refiner）**
- 输入：当前 strategy，以及范围内 T 题注入前后的对比。对比包括：变好的题 4 道、变差的题 4 道、仍然失败的题 2 道，均压缩为公开轨迹。
- 输出：修订后的 strategy 和一句修改说明。只针对证据中可观察到的差异修改，不新增与证据无关的规则。
- 每个候选最多修订 2 次；每次篇幅最多比上一版增加 30%。修订后只在范围内的签名组上重测，不扩大范围。

**第 5 步：编写并校准路由（Router）**
- 输入：
  - 目标操作说明；
  - T 中签名属于范围的题面（正例，最多 12 道）；
  - T 中签名属于排除集或其余组的题面（反例，最多 12 道，优先选第 3 步伤害检查涉及的组）；
  - 当前库中其他卡的 when_to_use。
- 签名字段本身不交给 Router，只给题面。when_to_use 要描述的是题目的样子，而不是标签。
- 输出：when_to_use，不超过 80 词，用操作语言描述，不出现领域词（程序检查，见 7.4 节）。
- 校准循环：
  1. 只跑 Selector（使用完整候选库，不跑 rollout）。
  2. 在 T 上按签名计算误选和漏选，把误选的反例题面和漏选的正例题面反馈给 Router。
  3. 最多迭代 3 次。
  4. 最后在 P 上核对，只计算聚合数字，不反馈给 optimizer。
- 通过条件：
  - P 上反例的误选率 ≤ 3%；
  - 正例的召回率 ≥ 60%；
  - 不让已有卡的召回率下降超过 10 个百分点。
- 每次 Selector 调用只是一次短 LLM 调用（约 1000 token 输入、7 token 输出），一千题只需几分钟。

**第 6 步：整库 Gate**
- 只跑 Selector，比较当前库与候选库在 G 上的选卡结果。
- 只重跑选卡结果有变化的题；没有变化的题直接复用缓存（E1、E2）。
- 判定规则见 8.3 节。

## 7. 大模型调用的输入输出规范

### 7.1 压缩后的公开轨迹视图（optimizer 三类调用共用）

| 字段 | 内容 | 上限 |
|---|---|---|
| 编号 | case_1、case_2 这样的局部编号；不出现题号、task 代号或 benchmark 名称 | — |
| 题面 | 题干与选项，去掉 benchmark 的指令外壳 | 原文 |
| 视频 | 视频 ID 与时长 | — |
| 每一步 | action；`analyze_videos` 的逐视频 instruction 原文；`watch_videos` 的 instruction 和片段；VideoAgent 报告的 Summary | 每条 Summary ≤ 600 字符，超出部分截断并标注“[truncated]” |
| 结果 | 最终答案、对错标签（pass/partial/fail）、Train 的正确答案 | — |
| 对比（仅 Refiner） | 同一题注入前后的轨迹并列展示 | — |

**不放入的内容**：
- Global 的 reason，篇幅大且多为重复；
- 原始路由事件、卡的全文副本、哈希、缩进空白。在 cv2r 中这些占输入的 50% 以上。

**总长度上限**：每次调用约 40K 字符。超出时按“题”整道丢弃，并在输出中标注丢弃了哪些题。上限要为后续追加的内容预留空间，避免 cv2r 那样作者输入超限、整个候选被丢弃。

### 7.2 决策点清单（Proposer 和 Refiner 的提示内容）

清单列出 GlobalAgent 层面可以改变的决策点，以及每个决策点的已知证据。optimizer 只需要选一个，写出具体做法：

1. **逐视频 instruction 的写法**：中性、可比较的描述，而不是“有没有 X？”（E4）；要求报告哪些可见细节；保留题目中的限定条件。
2. **动作选择**：何时用 `analyze_videos`、何时用 `watch_videos`；联合观看时传哪些视频、怎样写 instruction（E6、E7）。必须遵守 action 规则，不能让视觉模型直接选答案；可以要求它逐个选项报告可见的支持或反对证据。
3. **片段与覆盖**：长视频是否先定位再细看；联合观看时视频越多，每个视频分到的帧越少。
4. **追问的触发条件**：报告分不出候选、或互相矛盾时，对哪几个候选、用什么样的问题追问（E4）。
5. **何时回答**：证据足够区分候选时停止。

清单不包含答案格式规则，因为回答器不接收 skill（E11）。

### 7.3 输出 Schema 与长度规则

| 调用 | 输出字段 | 程序检查 |
|---|---|---|
| 签名标注 | `answer_form`、`operation`、`evidence_scope`（枚举） | 枚举合法；无法判断时用 `other` |
| Proposer | `decision_point`（清单中的编号）、`target_operation`（≤ 40 词）、`strategy`、`expected_change`（≤ 60 词） | 两个候选的 `decision_point` 必须不同；长度；领域词和泄漏检查 |
| Refiner | `strategy`、`change_summary`（≤ 60 词），或 `skip` 加理由 | 与原文不能相同；长度和增幅；领域词和泄漏检查 |
| Router | `when_to_use`（≤ 80 词） | 领域词检查；不能出现 task 代号或 benchmark 名称 |

**strategy 的长度**：
- **硬上限 600 词**（运行时原有上限 1200 词）。
- prompt 中建议 150–350 词，并且只针对一个决策点。
- 每次修订，篇幅最多比上一版增加 30%。
- 每张卡都记录长度和测得的效果，阶段 1 结束后据此复核上限。
- 这样设定的理由：没有数据能说明某个具体数值最好；但 cv2r 的卡在修订中从 420 词膨胀到 851 词而没有收益，项目旧结论也记录了“Generator 容易写出超长、领域过窄的卡”，所以不建议完全不设限。

所有调用都按现有方式保存输入、原始输出、校验结果和 usage，可以恢复。按项目规则，英文 prompt 同时维护中文镜像（`chinese_prompts/`）。

### 7.4 程序检查

- **领域词**：when_to_use 中不能出现 CrossVid 的领域词，例如烹饪、食谱、电影、角色、无人机、UAV、装配、玩具车。strategy 中出现时只给警告，因为方法内容可能确实需要举例。词表在实现时从 T 题面的高频名词中整理，并人工核对。
- **泄漏审计**：strategy 和 when_to_use 中不能出现视频文件名、视频 ID 以外的媒体标识、T 题的具体时间点；与 T 中报告原文的 8-gram 重合不能超过 3 处。
- **一致性**：when_to_use 声明的操作必须出现在 `target_operation` 中。由 Router 的输入保证，再由第 5 步的实测选卡结果核对。

## 8. 统计与判定规则

### 8.1 “变化”的定义

沿用 `scoring.py` 的 `CHANGE_MARGINS`：
- 选择题：对错翻转才算变化；
- FSA：IoU 变化 ≥ 0.2；
- CCQA：变化 ≥ 1/3。

变好题数记为 b，变差题数记为 w。

### 8.2 Probe 的序贯判定（每个候选、每个签名组）

- 每块 50 题，块内按 task 分层，顺序按固定种子打乱后冻结。
- 每测完一块检查一次：
  - **成功**：单侧符号检验 p ≤ 0.05（只看变化了的题，b 对 w）→ 该签名组进入范围；
  - **放弃**：w ≥ b + 3 → 该签名组进入排除集，停止测量；
  - 其他情况继续测下一块，测完上限仍未成功，记为不显著。
- 参考检出能力（取翻转率 d=0.17–0.33）：
  - 200 题约可检出 +6–9 分；
  - 300 题约可检出 +4–6 分；
  - 600 题约可检出 +3–4 分。
  - 效果更小的卡，在这个预算下测不出来，会被标为不显著。

### 8.3 Gate 的接受规则（用户已确认）

对候选库与当前库在 G 上逐题配对，同时满足三条才接受：

1. G 上的官方总分提高：CrossVid task 等权 macro，子集上按全集 task 题数分层估计，与 `HierarchicalScoreAggregator` 口径一致；
2. 选卡有变化的题上，单侧符号检验 p ≤ 0.10；
3. 没有任何一个 task 出现 w ≥ b + 3。

第 2、3 条是对“只看官方总分”的统计化解释：仍然只看官方总分，但要求提高的幅度超出扰动噪声。

### 8.4 多重比较

Probe 会对很多签名组和候选做检验，必然有假阳性。由于 G 的题与 P 不重叠，Gate 起到独立确认的作用；最终的结论只依据 G 和 Test，不依据 P。

### 8.5 报告

每次对比都报告：
- 各签名组的 b 和 w，各 task 的官方分差；
- 选卡率（按签名组和 task 分别统计）、答案合法率；
- 被注入的题数、安慰剂的翻转率；
- 卡的长度。

## 10. 实施计划

**阶段 0：基础设施**（时间预算 2 天；主要在本机写代码，GPU 只用于签名标注和最后的冒烟测试）

1. 签名标注：prompt、schema、批量执行，以及 5.5 节的三项质量检查。
2. 切分脚本：生成 T/P/G 的 manifest，包含来源隔离、MOC/MSR 按序列抽取、P 按签名组抽取、G 按 task 分层，并输出可行性报告。
3. Probe 执行器：强制注入，复用 `FrozenMVAgentExecutor` 和 rollout 缓存；核对静态注入与动态注入的渲染文本逐字相同。
4. Selector-only 执行器：直接调用 `select_skills`，不跑 rollout。
5. 配对统计模块：计算 b、w、序贯判定、官方分差、合法率，复用 `aggregation.py`。
6. 压缩轨迹视图：复用 `infra/trajectory.py` 的公开轨迹投影，增加长度上限、局部编号与丢弃记录。
7. 三类 optimizer 调用的 prompt、schema 和中文镜像。
8. 状态持久化与恢复，复用 `infra/store.py`。
9. Modal 冒烟测试：20 题跑通完整的一轮，并贴出实际输出。

**阶段 1：第一个端到端实验单元**（时间预算 1 天，GPU 约 8–10 h）

依次完成：签名标注与切分 → 空库 rollout → 复用检查 → 安慰剂标定 → `check_condition_per_video` 签名组的一个完整循环 → Gate。

产出：
- 主指标：G 上的官方总分变化，以及各签名组、各 task 的 b 和 w；
- 范围、选卡率、合法率、卡的长度；
- 更新 `.claude/status.md`。

无论结果正负，都如实记录。

**阶段 2：扩展到其他签名组**

候选顺序（按迁移价值和已知杠杆排列）：
1. `order_events`（对应 CVBench 时序推理和 MVU TR 中的排序题）；
2. 需要联合比较的组（`compare_across_videos` 中 `evidence_scope=joint` 的题，对应 E7 中 agent 落后 E2E 的题型）；
3. `locate_interval`（只在 CrossVid 中出现）；
4. `count` 与 `spatial_relation`；
5. 其余组。

每个组沿用阶段 1 的循环；Gate 用整个库的 G。

**阶段 3：独立评估**

- 冻结最终库，在 Lite2500、CVBench、MVU-Eval 上分别与空库对比。
- 标注 Test 题的签名，报告各签名组的覆盖率、选卡率、b/w 和官方总分。
- 在 Lite2500 上按“视频来源是否与训练用视频重叠”分组比较涨幅。T 全部来自干净池，理论上没有重叠；如果后续阶段放宽，就用这个比较估计泄漏的影响。

**停止条件**：每个阶段超出时间预算时，先缩小非必要范围（减少候选数、减少保护组的题数），不放弃端到端测量。

## 11. 风险，以及目前不能声称的结论

- **效果可能小于检出能力。** 历史上手写的 skill 都没有显著效果（E9）。可能的结果是没有任何卡通过 Gate；这本身就是有价值的负结果，会如实记录各候选的 b、w 和置信区间。
- **签名可能不准或不稳定。** 标注错误会让 Probe 的组混入不相干的题，稀释效果；也会让路由校准的标签出错。阶段 0 的质量检查会给出一致率；如果某个字段不稳定，就不用它分组。
- **签名组内部可能仍不均匀。** 一张卡也许只对组内的一部分题有效。第一阶段不再细分；需要时再按 `answer_form` 或 `evidence_scope` 拆分。
- **强制注入与自然选卡之间有差距。** Probe 测的是对整个签名组都注入的效果，自然选卡时只有一部分题会被选中。Gate 测的是自然选卡，两者可能不一致，以 Gate 为准。
- **Selector 在 CVBench 和 MVU-Eval 上的行为未知。** 两者是纯 Test，只能在阶段 3 看到结果。签名的设计让路由依据操作而不是模板，但这一点要到阶段 3 才能验证。
- **回答器的格式失败不修**（5.4 节）。卡如果改变了 `reason` 的长度，可能通过截断率影响分数。这一项会被监测，但无法从分数中完全剔除。
- **确定性依赖于固定的硬件和并发设置。** 换卡、换 vLLM 版本或改并发都会破坏缓存复用，必须重新做复用检查。

**目前不能声称**：任何 Global skill 能带来净提升；CrossVid 上训练出的卡能迁移；联合观看在全体题目上有净收益。

- 第一阶段预算：GPU 约 8–10 h，约 300–400 美元。
- 回答器不修。
- 系统在训练和推理中都看不到 task 类别。

**待确认**：
1. 用题型签名取代 task 作为分组、范围和路由的单位（5.5 节）。签名字段和取值可以调整。
2. strategy 长度规则：硬上限 600 词、建议 150–350 词、每次修订增幅 ≤ 30%（7.3 节）。

## 附录 A：与 cluster_v2 的对比

| 方面 | cluster_v2 | 本方案 |
|---|---|---|
| 组织单位 | 题面 embedding + Louvain 聚类 | Actor 模型只读题面得出的题型签名 |
| 适用范围 | 作者在 when_to_use 中声明 | 由强制注入的实测净收益决定 |
| optimizer 调用 | analyzer → planner → generator/reviser，每次输入 30–100K 字符 | Proposer、Refiner、Router，每次输入 ≤ 40K 字符；判断交给测量 |
| optimizer 可见数据 | Train，以及 Cal 题连同 GT | 只有 Train，且不含 task 代号和题号 |
| 候选评估 | 整库在 Cal 上评估（每类 4 题） | 按签名组序贯 Probe（每块 50 题，上限约 600 题） |
| 接受规则 | Gate 总分严格提高 | Gate 总分提高，且提高幅度超出扰动噪声 |
| 扰动的处理 | 无 | 安慰剂标定；逐题配对 |
| 路由 | 由作者撰写，不做检查 | Selector-only 校准，误选率 ≤ 3% |
| strategy 长度 | 上限 1200 词（实际膨胀到 851 词） | 硬上限 600 词，建议 150–350 词，修订增幅 ≤ 30% |

**可复用的部分**：`infra/` 中的 rollout、缓存、评分、聚合、公开轨迹投影和持久化；`mvagent/skills` 的运行时和 Selector；cluster_v2 中的 CARD_CONTRACT 和 action 背景说明（作为 prompt 素材）。
