# MVAgent 研究交接：在新服务器继续 Skill 自进化

本文是新接手研究员的入口，整理于2026-10-22。代码可以在普通GPU服务器运行，不要求使用Modal。此前计算环境已无法继续承担GPU实验；历史原件能否取回，与新服务器能否运行代码是两件事。数据准备见[数据获取与预处理](data-preparation.md)，安装、配置和运行命令见[服务器运行指南](server-runbook.md)。

当前研究结论是：**Skill已能实际改变MVAgent的选卡、行动和答案，存在值得确认的正信号；尚未证明当前自进化流程稳定优于强一次生成或简单提示控制。** 接手后应保留完整负结果，不预设“机制一定有效，只是生成器还不够好”。

## 1. 项目解决什么问题

输入是一个问题及多个相关视频，答案需要结合不同视频的信息。主要困难是信息量大、上下文长，以及决定答案的事实分散。MVAgent将全局协调和局部视频取证分开：

- **GlobalAgent**只先看到问题、视频ID和时长，通过`analyze_videos`并发下达各视频的instruction，通过`watch_videos`联合观看指定片段，通过`answer`直接提交最终答案。
- **VideoAgent**与视频一一对应，使用`observe`指定what、时间范围和FPS，使用`finish`返回局部报告。正常finish前至少有一次成功观察。同一视频多次被调用时保留自己的Memory。
- Global看不到Video内部轨迹；Video看不到Global的其他上下文，也看不到其他Video的内容。信息必须显式通过instruction和返回报告传递。
- `watch_videos`至少选择两个不同视频，片段共享本次帧预算，不接收FPS参数；Video的observe则对各范围分别读取，runtime会按容量限制调整采样。

研究期间冻结Actor权重、基础Prompt、动作接口和评分，只编辑skill文本。改变Actor预算或模型服务数值设置的实验应单列，不能把其差值归因于skill。

### Skill如何被使用

卡片为schema v3：`meta={id, role, stages}`、`when_to_use`、`strategy`。运行时按角色和阶段过滤；超过8张候选时用BM25与embedding融合召回8张，再由Selector最多选一张，也可不选。**只有strategy注入Actor，when_to_use用于检索和选择。**

| 消费者 | 实际可见内容 | 写策略时必须遵守的边界 |
|---|---|---|
| Global首次Selector | 问题、视频ID/时长、候选入口 | 尚无观察结果，不能要求它判断未来报告是否冲突 |
| Video每次请求Selector | 当前instruction、候选入口 | 不包含Video Memory、Global原题或其他视频内容 |
| Global Actor | 本题、视频信息、公开行动历史和返回报告、选中strategy | 不可直接查看Video私有观察轨迹 |
| Video Actor | instruction、源时长、本视频Memory、选中strategy | 不可猜测未传入的跨视频事实 |

Global整题、Video单次请求沿用第一次选择，包含none；观察后的条件分支应写在strategy中，不依赖在线换卡。Video耗尽步数的强制总结不自动携带规划skill；Global强制终答保留已选strategy。Observer也不会自动看到skill，执行要求必须经instruction、`observe.what`或watch instruction传递。详见[运行时机制](../src/mvagent/skills/README.md)和[卡片规范](../src/skill_evolution/skill_specification.md)。

## 2. 当前代码已经实现到哪一步

| 位置 | 已实现的职责 |
|---|---|
| `src/mvagent/` | Global/Video、Memory、动作执行及全局编排 |
| `src/mvagent/skills/` | 检索、Selector、选择缓存和策略注入 |
| `src/models/` | 模型客户端、固定本地推理服务与模型池 |
| `src/skill_evolution/configs/` | 方法配置解析、手工机制诊断卡定义 |
| `src/skill_evolution/infra/` | 库编辑与冻结、角色公开投影、模型调用留存、反馈组织 |
| `src/skill_evolution/algorithms/one_shot/` | 无题目、轨迹或成绩的一次生成 |
| `src/skill_evolution/algorithms/rolewise/` | 单角色单卡编辑、角色轮换和完整Cal/Gate接受 |
| `eval/agent_eval/`、`eval/skill_eval/` | 批量问答、原生评分、方法与评测适配 |
| `scripts/generate_skills.py`、`scripts/evolve_skills.py` | 一次生成和角色轮换入口 |

一次生成只读取角色契约、当前Actor基础System与动作预算；默认每角色一次调用，自主生成1–8张，`--max-cards`是上限而非配额。DeepSeek的14张冻结卡已经收入源码，保留它们不表示其性能已通过接受。

rolewise从Global/Video两个空库开始，按配置轮换角色，每次只对当前角色的一张卡执行add/revise/remove/noop。每个有效候选完整自然运行Train和Cal；Cal严格高于父库的最高分候选进入Gate，Gate官方总分严格提高才接受。伙伴库保持不变，失败候选不隐式累加。默认配置是2轮×2候选，历史正式实验是4轮×2候选，不能混用。

以下能力**尚未实现或未接入默认闭环**：

- 跨角色轮次的失败经验记忆、累计案例曝光管理、多父候选搜索、训练router、Video局部真值奖励。
- `infra/feedback.py`已有完整事件保留表示，曾用于独立格式对照；默认rolewise仍调用`infra.trajectory.examples`。可选Train汇总字段也不等于默认流程已发送完整汇总。
- 公共进化CLI没有`--initial-bank`或`--reuse-baseline`，旧实验基线复用通过私有冻结驱动接入。不能任意复制`evaluation.json`后宣称已经合法续跑。
- 完整SkillOpt/GEPA适配、预算匹配的多次搜索比较、独立最终Test均未完成。

当前方法源码最近一次远端验证包含compileall和17个测试文件；这不替代新服务器的依赖、实际模型身份及小规模运行验证。具体命令与配置字段以[方法README](../src/skill_evolution/README.md)和服务器指南为准。

## 3. 数据权限、分区和指标

Skill优化使用CrossVid。CVBench/MVU-Eval不进入optimizer，留作方法和库冻结后的最终评估；已有全量评测的历史接触必须披露，不能将曾查看的结果重新称作从未接触的盲测。

| 分区 | 用途 | 历史规模与限制 |
|---|---|---|
| Train | optimizer唯一可读的逐题反馈 | 80题，十任务各8；多轮重复使用 |
| Cal | 完整候选库筛选 | 40题，十任务各4；二值任务一题翻转可使总macro改变2.5pp |
| Gate | 正式接受或预声明只报告对照 | 176题；已是开发集，不是最终Test |
| 补充365 | 冻结策略扩大确认 | 96个声明来源组；8任务各40、PI14、PSS31；仍属开发确认 |
| 后续400 | 已准备、尚无已核实测量 | 十任务各40，seed0，题号与旧661及Lite2500不重叠；来源不独立 |

旧296与补充365合计661个不同题号。后续400中339题与旧661共享来源组，296题与Lite2500共享来源组，两项可重叠。全来源图排除旧661触及组件后，CC/CCQA/FSA/NC均无剩余题，故此前计划的严格十任务新来源确认无法按原条件构造；不能放宽后仍沿用“来源外确认”的名称。

优化器只接触Train中目标角色实际可见的公开投影、整题得分及卡库契约；不给GT、Judge评分点、题号、task代号、预设题型分类或Cal/Gate逐题内容。Video得到的是弱下游反馈，不能将整题0分解释为某份局部报告必然错误。只有instruction、视频及先前Memory相同，局部前后轨迹才可严格配对。

CrossVid主指标是**十task等权macro**，CCQA任务内按评分点加权，不是所有问题的普通平均。自然选卡、固定注入、离线查表和纯Selector调用要分别报告。原始rollout先保存再评分；Judge与基础设施失败报错，不能记为零分。接受规则只看官方总分，不额外加入成本或步数目标；接受不等于统计显著或稳定泛化。

统计报告保留原分。同题、完整Judge身份和请求相同时才做canonical敏感性比较，不覆写旧分数或历史接受。已有bootstrap区间未校正反复开发、多重比较；来源组区间也依赖分组假设。重复评估题次不增加独立样本。

|---|---:|---:|---:|
| 9B | 62.8887 / 64.4935 | 48.3004 / 50.5482 | 36.1005 / 35.2815 |

表中为百分比。九个比较四正五负，四个正差的探索区间均跨零，未显示该库一致带来收益。原始精简答案、文本轨迹、选卡事件与评分已公开，见[最终报告与Release](deepseek-skill-full-results.md)。这批与下面的角色轮换研究分开计数。

### 4.2 第一轮机制探索与角色轮换：已收束

2026-10-21至22日完成8881个评分题次，覆盖661个不同开发题：9B受控44单元5555题次、正式角色轮换1136题次、27B/35B迁移2190题次；另有960次纯Selector调用。全部该轮GPU已在当时释放。

| 9B自然运行 | Train80 | Cal40 | Gate176 |
|---|---:|---:|---:|
| 既有空库 | 25.2885% | 32.6186% | 32.4078% |
| GLM无反馈一次生成单Global卡，87c432… | 31.5648% | 25.7246% | **38.9940%** |
| 正式4轮×2候选后保留库，476532… | 27.7885% | **35.0000%** | 35.0869% |

八个正式候选仅首Global被接受，最终Video仍为空。强一次生成在Gate相对空库+6.5862pp，逐题和来源组探索区间为正；但Cal较低、与正式库的Gate差值区间跨零，且是已被关注的单次生成结果。它是需要保留的正信号，不是一次生成分布普遍更好或自进化有效的证据。

已测到的机制线索包括：

- 固定注入时间锚点卡，Train80相对空库+11.19pp；联合比较卡+9.00pp。但terminal一句“Answer from supported evidence in the requested format.”也有+6.66pp，不能把全部增益归于复杂程序。
- 同一时间卡自然选卡只选中21/80题，错过了固定注入在部分弃选题上的净收益；同时弃选也避免了一些退步。更高选中率不是收益保证。
- 更强Selector的12种路由查表均低于最佳常量策略；这些是映射到9B保存结果的诊断，不是新混合模型系统的准确率。
- Global与Video的单独正差不能相加；一项组合的收益反而下降。伙伴库变化会改变下游经验。
- 首接受Global正文删去复核阶段后，选择保持一致，105道共同选中题的动作全部变化、76道答案变化，但Gate净差接近零。已改变行为不等于已改善决定答案的证据。

所有条件、区间和审计范围见[完整探索结果](skill-exploration-results.md)，历史执行账本见[旧轮交接](skill-research-handoff-20261022.md)。

### 4.3 为什么扩样和迁移没有保留优势

365题主对照是**固定注入terminal一句提示**，不是none。旧365空库有两处短片媒体处理差异，只能作次参考。不能把早期对空库的增量直接与后来对terminal的差值相减。

| 模型 | terminal控制 | 固定时间卡 | 自然首接受库476532… |
|---|---:|---:|---:|
| 9B | 36.4594% | 34.7732% | 34.0246% |
| 27B | 51.6696% | 50.0520% | 48.3803% |
| 35B-A3B | 43.0428% | 43.4703% | 42.7994% |

各对应差值区间均跨零，未确认稳定优势，也不能称等效或稳定损害。自然库迁移同时改变Actor与Selector；27B和35B-A3B架构不同，不能由参数总量推断效果。**Gate38.99%的强一次生成87c432并不是该表的476532库，其新400题确认尚未测得。**

现有证据支持关注四个问题：小面板和多次候选选择可能放大早期正差；改善与损害相互抵消；预期策略有时没有按设想执行；选卡依据主要是语义适用，而不是当前Actor上的相对效用。它们是有证据约束的解释，不是已经完成的因果归因。

### 4.4 “强制watch救回47%”仍未精确复现

最初观察针对“E2E正确而MVAgent错误”的筛选子集，在Prompt中强制直接watch后约47%答对。目前没有找到并按同题清单、同模型、同基础Prompt及原强制文本完成精确复现。

后来watch-first固定卡测的是完整80题和365题：80题为30.7192%，相对空库+5.4307pp，19改善/12退步/49同分；365题为30.9523%，低于terminal的36.4594%，差值区间仍跨零。这些结果不能确认或否定原47%的错题恢复率。

如果恢复该方向，先找回原题号、原干预和执行协议。若原件不存在，应明确新做“错题恢复诊断”，同时报告救回与对原本正确题的损害；不要从筛选错题的恢复率推导总体增益，也不要按本次干预的结果再筛题。

### 4.5 第二轮反馈组织对照：十二库均有完整保存成绩

## 6. 接手后的研究顺序

下一轮执行以[最小实验矩阵](skill-experiment-plan.md)为准：先固定两库400题，再以9B检验同预算独立搜索与经验驱动进化；
只在有信号后开展关键消融、Video增量及最终评估。下文保留方向说明，不代表需要把所有建议同时运行。

### 第一步：确认可接续的基点

先按服务器指南验证数据输入、实际服务身份和一个最小完整问答。新服务器使用H20，可用数量波动，由接手研究员按实际分配配置Actor与Judge；不要求固定8卡或7+1分工。固定权重、推理seed0、温度0、thinking关闭、2048输出token、Global/Video各5步、512帧、最长边448。历史对照使用H100/BF16/TP1/单副本并发1、关闭prefix与MM processor cache；H20不能仅因模型名相同就默认与该历史数值环境一致。硬件、依赖或调用路径改变，应对受影响部分做小规模复核并保存新身份；不要因日期变更重复验证已通过的无关部分。

十二个格式/direct臂已有完整保存成绩，不要因旧05:33状态重跑Video。进一步复核Video需要读取原始结果并做已声明配对分析，不需要重做推理。真正中断的其他实验只有按冻结源码和配置恢复才叫resume；若环境无法保持原身份，在新目录登记为新运行，不覆写原结果。只有原件与当前协议、输入、模型/Judge身份匹配，才复用旧基线；不能为了少跑GPU而默认结果可交换，也不无依据重跑已完成基线。

### 第二步：优先回答尚缺的核心比较

原87c432与476532库及400清单已完整取回；数据媒体和服务准备完成后，先做已声明的固定两库开发确认，不因中途成绩换库或追加赢家搜索。它比较两个已保存库，不证明生成方法分布孰优，也不构成来源外Test。在H20上保存新的硬件与服务身份，不能把跨硬件的历史分数直接混成同协议的配对对照。

旧47%现象是另一个具体诊断方向，优先级取决于原实验材料能否找回。其精确复现与上述库比较是不同问题，应分别记录分母、对照和结论。

### 第三步：把进化改为真正利用已有经验

新的算法修改优先收窄到一个可检验问题：**跨轮保留Train中的编辑经验，并区分选卡失败、行为未变、行为改变后得失。** 每次提案记录假设、实际选择、首次行动差异及结果；案例轮换加入确定性轮次索引，记录累计曝光。保留成功参考、未激活和退步案例，不能只展示有利证据。对照同预算无反馈重新生成，避免把更多尝试误当作反馈价值。

Global与Video继续分开编辑、固定伙伴，但使用不同的分析重点：

| 角色 | 优先假设 | 有用的Train证据 |
|---|---|---|
| Global | 补齐委派中的身份、时间与跨视频依赖；按缺失事实决定委派或联合观看 | Global真正看到的问题、instruction、报告与行动差异 |
| Video | 保持instruction范围；定向补看；不把未确定改写成不存在、不把退化观察扩写成叙事 | 同instruction/视频/先前Memory的局部配对；观察与报告的文本支持关系 |

这些方向有轨迹依据但没有已证收益。报告完整进入Global的517/517审计排除了该样本中的传输丢失；它不证明报告真实。局部文本风险标记只是选例代理，不是Video正确性标签。不要通过给optimizer视频、GT或其他角色私有记忆来绕过当前研究边界。

每个候选只改一个主要假设，保持入口/正文/伙伴/Actor预算中其余因素稳定；仍按完整库自然运行验收。增加事前冻结的Cal覆盖，继续报告全部拒绝和负结果。不能把高Train、更多选中、更多watch或更长报告当作接受条件。

- 一个写清实际阶段、主指标、唯一主要阻塞和下一可执行动作的交接更新。启动、测试通过和提交成功都不能写成实验主目标完成。
