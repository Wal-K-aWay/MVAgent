## 2. 搜索并未持续吸收八个候选的经验

[optimizer.py](../src/skill_evolution/algorithms/rolewise/optimizer.py)每轮重新设置`last_train=None, last_edit=None`。一轮两个候选中，第一个只看已接受父库的例子；第二个看父库和本轮第一个候选的配对Train反馈。两个编辑都从同一个父库出发。

被拒候选及其假设虽已保存，却不会进入下一轮Prompt。角色轮换本身没有跨轮失败记忆。此次只有首Global接受，之后父库始终不变；因此不能把八个候选写成八层连续自我改进。实际重复的两个Video请求已由§1.1核实。

选例随机序列只使用`seed + attempt`，不含轮次。父库、角色相同且attempt回到0时，会再次选择相同问题与局部请求。重复Prompt的输出可以因GLM采样而不同，但这相当于同一证据下再采样，不能算吸收了上一轮的失败。

最小改进方向：保留固定推理seed；给例子轮换加入确定性的轮次索引，记录累计案例曝光；只以Train公开信息整理少量已测修改及得失，不把Cal/Gate逐题细节送入优化器。跨轮记忆是否有效应单独比较。

## 3. 轨迹整理已有角色隔离，但相关性和结构保护不足

[trajectory.py](../src/skill_evolution/infra/trajectory.py)没有把完整raw、图片Base64、token数组、HTTP日志塞给optimizer。Global复用实际公开History渲染，Video按角色投影自己的instruction和观察。这些是已完成的部分。

不足主要在以下几处：

1. **整题分数变化不等于选中了本次修改，也不等于当前角色行为改变。** 当前排序只优先分数变化和低父分题，按父失败与父满分约2:1取例。没有先区分卡片未激活、激活但行为未变、激活后改善或退化。
2. **Video每题随机选一个父请求。** 某题有多次Video调用时，展示的请求可能与修改无关。应该优先寻找可严格配对且实际行为变化的请求，同时保留明确标记的漏选案例，不能只筛成功激活题。
3. **Video局部不匹配时只给父轨迹和分数差。** `candidate_context_changed=True`能够防止错误配对，但候选实际做了什么没有呈现。这类例子有系统弱反馈，不具备局部前后对照的信息量。
4. **长轨迹按JSON字符串首尾截断。** 12000字符由各臂平分，父子配对通常每臂6000。截断可能保留问题与答案却删掉中间取证，不保护完整action、指令、错误和返回报告的边界。
5. **成对轨迹重复公共内容，没有突出行为差异。** 当前不是给出经过整理的比较表；优化器需要从两个序列自行恢复分歧和后果。应保护共同上下文、首次分歧及其直接结果，不把下游不同状态强行对齐为同一步。

建议使用确定性的事件抽取，避免先增加一个LLM摘要器。若预算装不下，明示被省略的事件范围。现有截断测试主要检查保留分数、两臂和`selected_cards`，没有验证决定性动作或证据保留。

## 4. Video投影存在条件性正确性问题

Video运行时对结构化输出无效的attempted observe使用`record_in_memory=False`，这类记录只进入当前请求的决策反馈。投影却将所有`action=observe`且有`result`的步骤加入重建Memory。遇到该情况时，它会把本不持久化的非法尝试带入后续请求的`prior_memory`，影响局部上下文哈希。

这是具体代码缺陷，不能仅称为Prompt风格。应区分：

- `status=invalid`的结构化决策错误：不能伪装成持久观察Memory；仍应在当前请求反馈中呈现。
- `status=error`的正常工具拒绝：运行时本来就记入Memory，不能一概删掉。

此外，当前投影丢掉非observe的非法决策、`output.error`，没有完整呈现正常finish与耗尽预算强制收束的区别。这会限制优化器对失败过程的理解。

最小回归例是“两次请求，首请求产生结构非法observe，第二请求检查prior Memory”，本次已在Modal CPU构造并确认投影与实际Memory不同。历史冻结运行不能热改；新投影需要与实际Actor可见记录一致。正确嵌套状态复核未发现本轮正式Train中触发这个缺陷，不能以它解释本轮负结果。

## 5. Prompt已有基础Actor契约，但消费条件仍不完整

| 已提供 | 尚未完整提供 | 解释 |
|---|---|---|
| 目标Actor真实System、真实动作说明、步数/帧数/range上限 | Actor型号、2048输出token、temperature=0、thinking关闭的简短摘要 | 不能说“没给基础Prompt”；但更强优化器未被显式告知文本将由哪个能力与预算的Actor执行 |
| Selector可见输入、最多一张/none、when与strategy的用途 | 真实Selector的四条规则及示例 | rolewise对选卡规则只有概述，未逐字包含“主要操作匹配、唯一候选也可拒选”等完整规则 |
| Video观察动作与源时间约束 | Observer的完整静态模板、时间映射与输出限制 | 可补接口摘要；不因此增加视频、GT或兄弟角色私有信息 |
| 逐题整题得分、Video弱下游反馈警告 | 分数范围/部分分、偏选案例不代表总体分布的明确说明 | 不应让优化器把八个刻意挑选案例的得失当作整库收益 |

rolewise只接收当前角色的库。伙伴策略的影响从本角色可见的指令和报告间接体现，这是信息权限与方法选择，不能简单把另一角色的私有轨迹补进去。

当前Prompt也没有整个Train的父/候选官方总分与改善/退化/不变计数。可增加紧凑的Train汇总，使刻意挑选的案例有总体参照；仍不能输入Cal/Gate细节，不能把每题普通平均冒充官方macro。

多数约束来自冻结架构和数据隔离，有必要保留。没有证据表明删去约束或放宽GT权限就能解决问题。更优先的是复用真实Selector静态提示、提供简短消费预算，并明确反馈语义。

## 6. 参数与验收的局限

- **搜索规模**：4轮×2候选，每角色实际仅4次提案；每轮仅第二个提案获得本轮前一次候选反馈。`max_cards_per_role=8`是上限，不代表进行了八卡库搜索。
- **案例规模**：每提案8例，不是完整Train80。案例数量与轨迹长度要一起看，不能通过单纯增大字符上限解决相关性和重复曝光。
- **Cal40**：十类各4题；二值任务的一道题翻转可改变总macro 2.5个百分点。首轮两个候选Cal同分，按稳定顺序选第一个。该规则符合原方案，但排序分辨率有限。
- **Gate**：八个候选中只一个进入正式Gate；后续候选没有超过父Cal，不等于它们都经Gate证明无效。Gate严格正点差接受也不代表稳定泛化。
- **优化模型**：实际配置为GLM-5.3、reasoning_effort=high、temperature=1、top_p=.95、max_tokens=16384。输出预算是否不足应看实际usage和finish_reason，不能只猜测；改温度是否有益也没有既有证据。
- **Actor预算**：9B、2048输出token、5步等是已冻结比较条件。没有独立预算消融，不能把改Actor参数混进skill改进后仍归因于skill。

原始rollout先落盘、Judge失败报错、完整自然选卡、同题官方评分及同身份缓存复用均有实现和已有核验。未发现足以把本轮分数整体作废的证据。需要修正的是对优化深度和学习信息充分性的描述。
